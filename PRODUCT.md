# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

Svelte 5 + Vite + TypeScript, client-side only. No SvelteKit, no SSR, no backend, no database. HTML Canvas 2D for visualization and Web Workers for sorting computation.

## Users

Students learning data structures and algorithms, developers who want an interactive algorithm demonstration, educators demonstrating sorting concepts, and curious users who enjoy visual experiments. They arrive with an image they care about and a question about how sorting actually works. They may be on a laptop in a classroom, at a desk while studying, or on a phone during a commute.

## Product Purpose

Pixel Sorting Visualizer turns an uploaded image into a sorting-algorithm playground. The user chooses how the image is divided into sortable elements, selects an algorithm, and watches the scrambled image rearrange live until the original composition is restored. The product makes algorithm mechanics memorable by replacing abstract bars and numbers with a picture the user chose. Success means a user can explain what the algorithm did, read the counters honestly, and trust that the final image is the original decoded arrangement.

## Positioning

The image is the data structure; the sorting algorithm is the process; live image reconstruction is the visualization. Unlike visualizers that sort colors by similarity, this product sorts elements by their original-position metadata, so every algorithm reconstructs the exact original arrangement. The same shuffled permutation can be replayed across algorithms for a fair comparison.

## Operating Context

The app runs entirely in the browser. Images are decoded locally, never uploaded. Users work with PNG, JPEG, and WebP files, choose individual pixels or 8/16/32/64/128-pixel blocks, and inspect comparisons, swaps, writes, reads, elapsed time, and algorithm complexity while the image rearranges. Playback supports play, pause, resume, single-step, reset, new shuffle, restore original, and speed control. Large workloads use batched playback and a Web Worker so the interface stays responsive.

## Capabilities and Constraints

- Granularity: individual pixels (1x1) and 8x8, 16x16, 32x32, 64x64, 128x128 blocks.
- Grid dimensions use ceiling division; partial edge tiles are valid sortable elements and must render without cropping or stretching.
- Element count is exact and shown before a run.
- Fisher-Yates shuffle with a seeded PRNG; reset restores the same initial shuffled permutation; new shuffle creates a new one.
- Algorithms are grouped by learning level. MVP: Bubble, Selection, Insertion, Merge, Quick. The library also includes Shell, Heap, Counting, Radix, and Bucket Sort.
- All algorithms sort the same stable element identity by target index and expose instrumentation through a shared event contract.
- No native `Array.sort()` in named algorithm implementations.
- Counters are generated by the algorithm, not inferred from frames. Total tracked operations = comparisons + reads + writes; swaps are reported separately and are not added again.
- Rendering reads are excluded from algorithm counters.
- Elapsed time excludes paused time; algorithm compute time is measured separately from rendering.
- Sorting runs in a Web Worker with batched events and bounded buffering. No unbounded event history.
- O(n^2) algorithms are discouraged or disabled above configurable workload thresholds.
- No accounts, cloud storage, social features, image editor, color-similarity sorting, or server-side execution.
- The final permutation is validated; the reconstructed image must match the original decoded arrangement.
- Responsive, keyboard-accessible, reduced-motion aware, and usable without relying on color alone.

## Evidence on Hand

No customer testimonials, benchmarks, or performance claims exist. Do not fabricate them. The PRD is the source of product truth. Performance thresholds are tunable configuration, not measured product claims.

## Product Principles

1. The image is the data structure, the algorithm is the process, and live reconstruction is the visualization.
2. Sort by original-position metadata, never by color similarity.
3. Accuracy over spectacle: counters, complexity, and completion states must be honest.
4. Keep the image local and the interface responsive, even when the workload is large.
5. Teach through the operation currently on screen, not through a dashboard of disconnected numbers.

## Accessibility & Inclusion

All controls keyboard accessible with visible focus states. Semantic labels for inputs and buttons. Do not rely on color alone to communicate compare, swap, write, pivot, or sorted states. Respect reduced-motion preferences. Provide textual operation descriptions for screen-reader users. Maintain adequate contrast. Canvas scales responsively without changing underlying image data.
